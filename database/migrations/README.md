Partimos de tu modelo base que ya definimos, pero vamos a hacer una actualización importante: **separar el schema de negocio (`app`) del schema de exposición (`api`)**.

Además, como todavía estamos en la primera versión, **no vamos a meter pagos, cuotas, eventos financieros ni actividades colaborativas**. Eso quedará para una segunda etapa.

## 1. Arquitectura de schemas

Propongo:

```text
PostgreSQL
│
├── public
│   └── schema_migrations
│
├── app
│   ├── organizacion
│   ├── persona
│   ├── usuario
│   ├── rol
│   ├── usuario_rol
│   ├── reunion
│   ├── asistencia
│   └── auditoria
│
└── api
    └── futura capa de exposición
```

La idea es:

* `app`: **datos reales del sistema**.
* `api`: lo que eventualmente expondremos mediante PostgREST.
* `public`: infraestructura, como el control de migraciones.

Tu PostgREST ya apunta a:

```yaml
PGRST_DB_SCHEMA: api
```

por lo que esta separación encaja perfectamente.

# 2. Primera migración: schemas

Vamos a cambiar la numeración.

### `001_create_schemas.sql`

```sql
CREATE SCHEMA IF NOT EXISTS app;
CREATE SCHEMA IF NOT EXISTS api;

REVOKE CREATE ON SCHEMA public FROM PUBLIC;

GRANT USAGE ON SCHEMA app TO anon;
GRANT USAGE ON SCHEMA api TO anon;
```

Pero aquí quiero hacer una precisión: **no necesariamente queremos que `anon` tenga acceso a `app`**.

Como PostgREST utilizará `api`, podemos dejar `app` protegido.

Por seguridad, recomiendo realmente:

```sql
CREATE SCHEMA IF NOT EXISTS app;
CREATE SCHEMA IF NOT EXISTS api;

REVOKE CREATE ON SCHEMA public FROM PUBLIC;

GRANT USAGE ON SCHEMA api TO anon;
```

Entonces:

```text
anon
 │
 └── api ✓

anon
 │
 └── app ✗
```

Esto es mejor.

# 4. Persona

### `003_create_persona.sql`

```sql
CREATE TABLE IF NOT EXISTS app.persona (
    id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    organizacion_id INT NOT NULL,
    nombres VARCHAR(150) NOT NULL,
    apellidos VARCHAR(150) NOT NULL,
    documento VARCHAR(50),
    telefono VARCHAR(50),
    email VARCHAR(254),
    estado BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_persona_organizacion
        FOREIGN KEY (organizacion_id)
        REFERENCES app.organizacion (id)

        ON DELETE RESTRICT
);
```

Relación:

```text
organizacion 1 ───── N persona
```

# 7. Usuario-Rol

### `006_create_usuario_rol.sql`

```sql
CREATE TABLE IF NOT EXISTS app.usuario_rol (
    usuario_id INT NOT NULL,
    rol_id INT NOT NULL,

    PRIMARY KEY (usuario_id, rol_id),

    CONSTRAINT fk_usuario_rol_usuario
        FOREIGN KEY (usuario_id)
        REFERENCES app.usuario (id)
        ON UPDATE RESTRICT
        ON DELETE CASCADE,

        FOREIGN KEY (rol_id)
```


# 9. Asistencia

### `008_create_asistencia.sql`

```sql
CREATE TABLE IF NOT EXISTS app.asistencia (
    id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    reunion_id INT NOT NULL,
    persona_id INT NOT NULL,
    codigo VARCHAR(100),
    fecha_hora_registro TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    fecha_hora_salida TIMESTAMPTZ,
    estado VARCHAR(50) NOT NULL,

    CONSTRAINT fk_asistencia_reunion
        FOREIGN KEY (reunion_id)
        REFERENCES app.reunion (id)
        ON UPDATE RESTRICT
        ON DELETE RESTRICT,

    CONSTRAINT fk_asistencia_persona
        FOREIGN KEY (persona_id)
        REFERENCES app.persona (id)
        ON UPDATE RESTRICT
        ON DELETE RESTRICT,

    CONSTRAINT uq_asistencia_reunion_persona
        UNIQUE (reunion_id, persona_id)
);
```

Esto produce:

```text
persona
   │
   │
   ▼
asistencia
   ▲
   │
   │
reunion
```

Conceptualmente:

```text
persona N ───── N reunion
       \         /
        \       /
       asistencia
```

La tabla `asistencia` es la que representa la participación concreta de una persona en una reunión.

# 13. Y ahora viene algo importante: no necesitamos crear tablas en `api`

Al menos **todavía no**.

`api` será nuestra capa de exposición.

Por ejemplo, posteriormente podemos tener:

```text
api.personas
api.reuniones
api.asistencias
```

como **vistas**, funciones o procedimientos, según lo que necesitemos exponer.

Así evitamos que PostgREST tenga acceso directo e indiscriminado a:

```text
app.usuario
app.auditoria
```

Esto nos da una arquitectura mucho más limpia:

```text
                CLIENTE
                   │
                   ▼
              PostgREST
                   │
                   ▼
                  API
                   │
                   ▼
                  APP
                   │
                   ▼
             BASE DE DATOS
```

## 14. Un detalle sobre `anon`

Tu `init/001-postgrest.sql` ya estaba relacionado con esto.

Ahora debemos evitar tener **dos lugares intentando crear/configurar los mismos schemas y permisos**.

Por eso propongo que dejemos:

```text
database/init/
```

para cosas necesarias para que PostgreSQL/PostgREST arranque, principalmente roles.

Y:

```text
database/migrations/
```

para la estructura versionada de nuestra aplicación.

## 15. Antes de ejecutar

Tu carpeta debería quedar exactamente así:

```text
database/
│
├── init/
│   └── 001-postgrest.sql
│
├── migrations/
│   ├── 001_create_schemas.sql
│   ├── 002_create_organizacion.sql
│   ├── 003_create_persona.sql
│   ├── 004_create_usuario.sql
│   ├── 005_create_rol.sql
│   ├── 006_create_usuario_rol.sql
│   ├── 007_create_reunion.sql
│   ├── 008_create_asistencia.sql
│   ├── 009_create_auditoria.sql
│   └── 010_create_base_indexes.sql
│
├── seeds/
│
└── scripts/
    └── migrate.mjs
```

Y **no ejecutes todavía `pnpm db:migrate`**.

Hay una última cuestión técnica que debemos resolver en tu `migrate.mjs`: actualmente crea:

```sql
public.schema_migrations
```

y eso está bien, pero quiero que también hagamos que el runner **valide que los nombres de migración tengan el formato `001_...sql`, `002_...sql`, etc.**, para evitar que algún archivo se ejecute fuera de orden.

Después de eso sí estaremos en condiciones de hacer la primera ejecución real.
